# Интеллектуальный диспетчер «Билайн Бизнес» (FSM / VRPTW & XAI)
> **Руководство разработчика команды | Внутренняя документация проекта**  
> Автоматическое построение расписаний выездных инженеров с учетом временных окон (VRPTW), квалификаций и транспорта, динамическое перепланирование по пакетам событий и объяснимый искусственный интеллект (Explainable AI).

## 📌 1. Архитектура и компоненты системы

```

                                       ▼ (HTTP :3000)

│  • Интерактивная фокусировка на сегментах доезда без сброса активного меню   │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ REST API (:8000)
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  backend (Python 3.10+ FastAPI + SQLAlchemy + SQLite)                       │
│  • Multi-tenant изоляция по Dispatcher ID (заголовок X-Dispatcher-Id)       │

                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  algorithm (Python 3.10+ FastAPI — Stateless Optimization & XAI Engine)     │
│  • Baseline FIFO Allocator (фиксация базовых метрик ТЗ)                      │
│  • Smart VRPTW Solver (минимизация штата + 2-opt оптимизация пробега)       │
│  • Batch Replanning Engine (атомарная обработка пачки событий без гонок)     │

```

## 🧪 2. Запуск в тестовом режиме (CLI / 100% Offline)

Для быстрой проверки алгоритма, отладки метрик, генерации тегов и ИИ-объяснений **без интернета, без базы данных и без поднятия серверов** создан скрипт [`test_cli.py`](file:///work/time-scheduler/test_cli.py).

### 2.1. Быстрый запуск CLI с датасетом по умолчанию (Восток)
```bash
./venv/bin/python test_cli.py
# или, если виртуальное окружение активно:
python test_cli.py
```

### 2.2. Запуск на встроенных пресетах
```bash
# Датасет Восток (67 заявок, 12 инженеров):
./venv/bin/python test_cli.py --preset vostok

# Датасет Югоцентр (57 заявок, 11 инженеров):
./venv/bin/python test_cli.py --preset yugcenter

# Датасет Юго-восток (84 заявки, 12 инженеров):
./venv/bin/python test_cli.py --preset yugovostok
```

### 2.3. Запуск на произвольном JSON-файле
```bash
./venv/bin/python test_cli.py --file path/to/custom_dataset.json
```

### 2.4. Тестирование модуля Explainable AI (ИИ-объяснения)
```bash
# Получить ИИ-обоснование по конкретной заявке:
./venv/bin/python test_cli.py --preset vostok --explain-task 53587

# Получить ИИ-обоснование по конкретному инженеру (маршрут или оперативный резерв):
./venv/bin/python test_cli.py --preset vostok --explain-engineer eng_vostok_3

# Распечатать обоснования по всем проблемным задачам и резервным инженерам:
./venv/bin/python test_cli.py --preset vostok --explain-all
```

### 2.5. Экспорт результата в JSON (для конвейеров и тестов)
```bash
./venv/bin/python test_cli.py --preset vostok --json > result.json
```

### 2.6. Интеграционный сквозной тест системы (E2E)
Для проверки всех REST API эндпоинтов backend и algorithm:
```bash
./venv/bin/python test_e2e.py
```

## 🚀 3. Как запустить проект полностью

### Вариант А: Локальный запуск скриптом (Рекомендуется для разработки)
Все сервисы поднимаются в фоновом режиме с логами в `logs/`:
```bash

# Остановить все процессы гарантированно (без дублирования):

```

**Терминал 1: Сервис алгоритмов (Порт 8001)**
```bash
source venv/bin/activate
cd algorithm
uvicorn app.main:app --host 0.0.0.0 --port 8001 --reload
```

**Терминал 2: Backend API (Порт 8000)**
```bash
source venv/bin/activate

uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

**Терминал 3: Frontend (Порт 3000)**
```bash
cd frontend
npm run dev -- --port 3000 --host
```

```bash
docker-compose up --build
```

## 🗄️ 5. Схема базы данных (SQLite)

БД автоматически создается в `backend/scheduler.db` и изолирована по `dispatcher_id`:

1. **`dispatchers`**: идентификатор сессии диспетчера (`id`, `active_preset`, `created_at`).
2. **`engineers`**: выездные бригады (`id`, `name`, координаты старта, смена `shift_start`/`shift_end`, навыки `skills_json`, транспорт `transport_type`, статус `active`/`unavailable`).
3. **`tasks`**: заявки на выезд (`id`, `address`, координаты, временное окно `window_start`/`window_end`, длительность `duration_min`, требуемый навык `required_skill`, требуемый транспорт `required_transport`, приоритет, статус `active`/`cancelled`).
4. **`schedule_records`**: сохраненные путевые листы (`engineer_id`, `task_id`, `order`, `arrival_time`, `start_time`, `end_time`, `travel_km`, `travel_min`).
5. **`plan_metrics_records`**: сохраненные KPI оптимизации (`total_mileage_km`, `total_engineers_used`, `mileage_reduction_pct`, `engineers_reduction_pct`).
6. **`explanation_cache`**: кэш ИИ-обоснований (`cache_key = {dispatcher_id}:{task_or_eng_id}`, `explanation_text`).

## ⚙️ 6. Ограничения и алгоритмический пайплайн

### 6.1. Обязательные ограничения ТЗ (Hard Constraints)
1. **Квалификация:** Требуемый навык заявки обязан строго входить в список навыков инженера:
   * *«Локальные работы»*
   * *«Работы на подключение и дозаказы»*
   * *«Аварийные работы»*
2. **Транспорт:** Если заявка требует автомобиля, назначить пешехода или велосипедиста запрещено:
   * *«Автомобиль»* (расчетная скорость: 35 км/ч)
   * *«Общественный транспорт»* (20 км/ч)
   * *«Велосипед»* (15 км/ч)
   * *«Пешеход»* (5 км/ч)
3. **Временные окна визита и смены:**
   * Время прибытия + длительность работ должны попадать в клиентское окно $[T_{window\_start}, T_{window\_end}]$.
   * Окончание выполнения последней заявки не может превышать `shift_end` инженера.

### 6.2. Базовый алгоритм (Baseline FIFO) vs Оптимизатор (VRPTW)
* **Baseline FIFO (Раздел 2.3 ТЗ):** Назначает заявки в хронологическом порядке их поступления первому доступному инженеру без перестроения очереди. Результат: высокий холостой пробег, задействован почти весь штат, часть задач не укладывается в окна.
* **Smart VRPTW Optimizer:** 
  1. Кластеризация и сортировка по срочности временных окон.
  2. Первичное назначение с минимизацией задействованного парка (неиспользуемые бригады уходят в оперативный резерв).
  3. Локальный поиск **2-opt** для устранения перехлестов и минимизации суммарного пробега.
  4. Сокращение пробега на **15–35%** и вывод в резерв **15–25%** штата с сохранением 100% выполнимости задач.

### 6.3. Пакетное перепланирование (`/replan`)
Принимает массив событий:
* `URGENT_TASK`: встраивание срочной задачи в маршрут ближайшего квалифицированного инженера.
* `ENGINEER_UNAVAILABLE`: сход инженера с линии — его задачи автоматически распределяются между коллегами.
* `CANCEL_TASK`: отмена заявки клиентом — моментальное удаление из цепочки и сокращение пути.

## 💡 7. Важные интерфейсные фичи для команды

1. **Сессионная привязка без авторизации:**
   Диспетчер идентифицируется ключом `disp_xxxxxxx`. Ключ сохраняется в:
   * URL адресной строки: `http://localhost:3000/?session=disp_xxxxxxx`
   * `localStorage`
   * `document.cookie`
   При клике на `(Новая сессия)` генерируется новый ID, сбрасывается кэш, обновляется URL и подтягивается чистый датасет.

2. **Синхронизация тегов и фильтров:**
   * Клик на карточку или тег инженера подсвечивает и фильтрует только его заявки в `TaskList`.
   * Клик на задачу в списке или на карте подсвечивает назначенного инженера в `EngineerList`.
   * Клик на бейдж навыка (например, *«Аварийные работы»*) мгновенно фильтрует специалистов и заявки по этому профилю.

3. **Светлая цветная карта (CARTO Voyager):**
   * Растровые тайлы CARTO Voyager обеспечивают высокую контрастность и детализацию дорожной сети Москвы.
   * Все маршруты имеют двойную обводку (белая подложка + сочный цвет линии) для идеальной читаемости.
   * Отмененные заявки отображаются серым цветом (`#475569`) с перечеркиванием.

4. **Фокусировка на сегменте пути без смены меню:**
   * Клик на блок доезда (🚗 X км, Y мин) в горизонтальном таймлайне или в путевом листе приближает камеру карты на конкретный отрезок движения и рисует акцентный пунктирный трек.
   * Клик изолирован (`e.stopPropagation()`), поэтому открытые карточки и выбранные табы не закрываются.

## 🛠️ 8. Решение типовых проблем (Troubleshooting)

* **Ошибка «Failed to fetch» на фронтенде:**
  Убедитесь, что backend запущен на порту 8000: `curl http://localhost:8000/health`.
* **Ошибка «LineString coordinates must have at least 2 coordinates»:**
  Инженеры без маршрутов (в резерве) автоматически исключаются из рендеринга путей. Проверено в `MapView.tsx`.
* **Зависшие фоновые процессы Python / Node:**
  Запустите `./stop_local.sh` — скрипт принудительно освобождает порты 3000, 8000 и 8001.
* **Пересборка фронтенда:**
  `cd frontend && npm run build` (сборка проверена, TypeScript strict mode проходит без ошибок).
