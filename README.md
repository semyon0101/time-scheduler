# Интеллектуальный диспетчер «Билайн Бизнес» (FSM / VRPTW & XAI)
> **Руководство разработчика команды | Внутренняя документация проекта**  
> Автоматическое построение расписаний выездных инженеров с учетом временных окон (VRPTW), квалификаций и транспорта, динамическое перепланирование по пакетам событий и объяснимый искусственный интеллект (Explainable AI).

---

## 📌 1. Архитектура и компоненты системы

Система построена на слоистой сервисной архитектуре с чистым разделением ответственности. Алгоритмический модуль VRPTW-оптимизации и Explainable AI встроен непосредственно в бэкенд, исключая лишние сетевые задержки и накладные расходы:

При оптимизации `backend/Services/routing/optimizer.py` вызывает однодневный OR-Tools солвер из `backend/Services/routing/solver.py` для каждого инженера. После каждого вызова назначенные заявки удаляются из общего списка; остальные предлагаются следующему инженеру. Затем ограниченный поиск вставок, переносов, обменов и цепочек вытеснения сравнивает **весь завершённый план** по лексикографическим сервисным приоритетам из `routing/policy.py`: промежуточный план с вытесненной заявкой не публикуется. Поиск ограничен числом проверяемых вариантов. DTO запросов и ответов находятся в `backend/Models/VRPTW/`. FIFO-план служит для сравнения на тех же участках, графике и окнах; проценты экономии пробега показываются только при одинаковом составе обслуженных заявок. FIFO и перепланирование используют ту же модель расстояний и времени пути из `routing/geo.py`. Проверка фиксированного порядка визитов для перепланирования находится в `routing/feasibility.py`.

Допуск к назначению: совпадение `area_id`, дежурство `is_on_duty`, статус, навыки, транспорт и временные окна. Категории `emergency`, `connection`, `repair`, `add_on`, `other` хранятся отдельно от поля срочности; для встроенных пресетов они берутся из поля «Тип заявки BK» исходных CSV, а каждый пресет считается отдельным участком. Дежурство всех инженеров пресета — явное демонстрационное допущение. Время поступления `created_at` отсутствует в CSV и **не выдумывается**: по этим заявкам реакцию измерить нельзя. Для новой заявки время поступления сохраняется при создании. 120 минут — мягкий ориентир реакции аварии, 60 минут — цель мониторинга, не договорный штраф и не запрет позднего назначения. Инженерское оборудование считается полученным на весь день; расход и пополнение запасов, а также денежная оптимизация в этой версии не моделируются.

## ⚙️ 2. Конфигурация окружения (.env)

Все параметры запуска и сетевые порты для деплоя настраиваются через файл `.env` в корневой директории проекта.  
**Сетевые порты задаются строго без дефолтных значений в коде/конфигах.**

### 2.1. Создание файла .env из шаблона:
```bash
cp .env.example .env
```

### 2.2. Подробное описание переменных:

| Переменная | Обязательная | Описание | Пример значения |
|---|:---:|---|---|
| `BACKEND_PORT` | **Да** | Сетевой порт, на котором запускается FastAPI Backend API. Используется Docker Compose, скриптами и Pydantic Settings. Дефолта нет. | `8000` |
| `FRONTEND_PORT` | **Да** | Сетевой порт веб-интерфейса диспетчера (React + Vite). Используется в Docker Compose и Vite dev-сервере. Дефолта нет. | `3000` |
| `POSTGRES_PORT` | **Да** | Внешний сетевой порт СУБД PostgreSQL. Пробрасывается в `docker-compose.yml`. | `5432` |
| `POSTGRES_DB` | **Да** | Имя создаваемой базы данных в контейнере PostgreSQL. | `scheduler_db` |
| `POSTGRES_USER` | **Да** | Имя пользователя суперпользователя PostgreSQL. | `postgres` |
| `POSTGRES_PASSWORD` | **Да** | Пароль пользователя PostgreSQL. | `postgres` |
| `DATABASE_URL` | **Да** | Полная строка подключения SQLAlchemy (диалект `postgresql://`). Для локального запуска: `postgresql://postgres:postgres@localhost:5432/scheduler_db`. Для Docker Compose контейнер backend подключается к хосту `db`. | `postgresql://postgres:postgres@localhost:5432/scheduler_db` |
| `HOST` | Нет | Хост для биндинга uvicorn сервера (по умолчанию `0.0.0.0`). | `0.0.0.0` |
| `RESPONSE_LIMIT_MIN` / `RESPONSE_TARGET_MIN` | Нет | Модельный ориентир реакции на аварию и цель мониторинга; по умолчанию 120 и 60 минут. | `120` / `60` |

> ⚠️ **Важно:** Переменная `ALGORITHM_PORT` удалена, так как вычислительный движок VRPTW и генератор XAI работают непосредственно внутри бэкенда в процессе Python.

## 🚀 3. Пошаговый запуск всего проекта

### Способ 1: Запуск полного стека в Docker Compose (Рекомендуемый для продакшна)

Поднимает PostgreSQL, Backend API и Frontend с автоматическим связыванием сетей и томов.

```bash
# Шаг 1: Клонировать репозиторий и перейти в корень проекта
cd /path/to/time-scheduler

# Шаг 2: Создать и настроить файл конфигурации .env
cp .env.example .env

# Шаг 3: Собрать и запустить все контейнеры в фоновом режиме
docker compose up --build -d

# Шаг 4: Проверить статус работающих сервисов
docker compose ps

# Проверить API напрямую и через прокси фронтенда
source .env
curl http://localhost:$BACKEND_PORT/health
curl -i http://localhost:$FRONTEND_PORT/api/v1/health

# Шаг 5: Просмотр логов в реальном времени (при необходимости)
docker compose logs -f

# Шаг 6: Остановка всех контейнеров с сохранением данных в томах
docker compose down
```

---

### Способ 2: Быстрый локальный запуск через скрипты из `scripts/` (Для разработки)

Автоматизирует одновременный запуск Backend и Frontend в фоновом режиме.

```bash
# Шаг 1: Подготовить виртуальное окружение Python (один раз)
python3 -m venv .venv
./.venv/bin/pip install -e ".[dev]"

# Шаг 2: Установить зависимости клиентской части Frontend (один раз)
cd frontend && npm install && cd ..

# Шаг 3: Создать файл .env (если еще не создан)
cp .env.example .env

# Шаг 4: Поднять базу данных PostgreSQL (если не установлена локально, можно через Docker):
docker compose up db -d

# Шаг 5: Запустить сервисы скриптом из папки scripts/
./scripts/run_local.sh
# (Или через корневой алиас: ./run_local.sh)

# Шаг 6: Для остановки всех запущенных сервисов выполните:
./scripts/stop_local.sh
# (Или через корневой алиас: ./stop_local.sh)
```

При первом открытии `/dashboard` сервер сразу строит маршруты для демонстрационного набора: ответ `/session/init` может занять около 25–30 секунд. Пока запрос выполняется, интерфейс показывает статус загрузки; если API недоступен, появится сообщение с кнопкой повтора.

### Способ 3: Ручной покомпонентный запуск (в разных терминалах)

**Терминал 1: База данных PostgreSQL**
```bash
docker compose up db
```

**Терминал 2: Backend API**
```bash
source .venv/bin/activate
source .env
uvicorn main:app --app-dir backend --host 0.0.0.0 --port $BACKEND_PORT --reload
```

**Терминал 3: Frontend**
```bash
cd frontend
source ../.env
FRONTEND_PORT="$FRONTEND_PORT" VITE_PROXY_TARGET="http://127.0.0.1:$BACKEND_PORT" npm run dev -- --host 0.0.0.0 --port "$FRONTEND_PORT"
```

* 🩺 **Health Check API:** [http://localhost:8000/health](http://localhost:8000/health)

### Оперативное перепланирование

`POST /api/v1/schedule/replan` принимает массив `events` с типами `REGULAR_TASK`,
`URGENT_TASK`, `CANCEL_TASK`, `ENGINEER_UNAVAILABLE`. Обычную заявку можно передать
в поле `task` либо сначала создать через `POST /api/v1/tasks`, а затем передать её
`task_id` в событии `REGULAR_TASK`. Пример для созданной заявки:

```json
{"events": [{"event_type": "REGULAR_TASK", "task_id": "task_123", "timestamp": "10:15"}]}
```

`timestamp` — `HH:MM` или ISO 8601 (при отсутствии берётся текущее московское время).
Пакет событий рассчитывается на время последнего события в нём. Расписание пока хранит
время без даты, поэтому события относятся к одному рабочему дню.
Обычная заявка вставляется без изменения исполнителей, порядка и начал уже выданных работ;
если места нет, она остаётся неназначенной. При аварии можно перестроить только ещё не
начатые визиты. Отмена начатой или завершённой работы отклоняется с HTTP 409.
Для удаления назначенной заявки её сначала нужно отменить; инженера с сохранёнными
визитами удалить нельзя.

## 🧪 5. Тестирование и верификация (CI/CD)

### 5.1. Модульные и интеграционные тесты (`pytest`)
Полный набор тестов для слоистой архитектуры (контроллеры, сервисы, репозитории, сущности, DTO-модели):
```bash
./.venv/bin/pytest tests/ -v
```

### 5.2. Сквозной E2E-тест (`test_e2e.py`)
Проверяет жизненный цикл сессии, загрузку пресетов данных, создание/отмену заявок, перепланирование, статус инженера оффлайн и Explainable AI:
```bash
./.venv/bin/python test_e2e.py
```

### 5.3. Автономный CLI-тест VRPTW и Explainable AI (`test_cli.py`)
Работает на 100% автономно без сети и без БД:
```bash
# Датасет Восток (67 заявок, 12 инженеров):
./.venv/bin/python test_cli.py --preset vostok

# Датасет Югоцентр (57 заявок, 11 инженеров):
./.venv/bin/python test_cli.py --preset yugcenter

# Получить ИИ-обоснование по конкретной заявке:
./.venv/bin/python test_cli.py --preset vostok --explain-task 53587

# Получить ИИ-обоснование по инженеру в резерве:
./.venv/bin/python test_cli.py --preset vostok --explain-engineer eng_vostok_3
```
