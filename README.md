## 🧠 4. Автономный CLI-стенд тестирования алгоритмов (`scripts/eval_algorithm.py`)

Скрипт [`scripts/eval_algorithm.py`](file:///work/time-scheduler/scripts/eval_algorithm.py) позволяет тестировать алгоритмы **100% offline без интернета и без запуска фоновых серверов**:

```bash
# 1. Быстрая оценка оптимизатора на пресете Восток:
./venv/bin/python scripts/eval_algorithm.py --preset vostok

# 2. Оценка на других пресетах Москвы:
./venv/bin/python scripts/eval_algorithm.py --preset yugcenter
./venv/bin/python scripts/eval_algorithm.py --preset yugovostok

# 3. Оценка на произвольном внешнем JSON датасете:
./venv/bin/python scripts/eval_algorithm.py --file path/to/dataset.json

# 4. Вывод ИИ-обоснования по заявке или инженеру:
./venv/bin/python scripts/eval_algorithm.py --preset vostok --explain-task 50219
./venv/bin/python scripts/eval_algorithm.py --preset vostok --explain-engineer eng_vostok_1
./venv/bin/python scripts/eval_algorithm.py --preset vostok --explain-all

# 5. Экспорт полного структурированного JSON-отчета:
./venv/bin/python scripts/eval_algorithm.py --preset vostok --json > report.json
```

### 4.1. Как протестировать СВОЙ алгоритм:
Чтобы проверить собственную функцию оптимизации или эвристику, напишите функцию с сигнатурой:
```python
def my_custom_solver(
    engineers: List[EngineerModel], tasks: List[TaskModel]
) -> Tuple[List[EngineerRoute], PlanMetrics, List[UnassignedTask]]:
    # Ваша логика распределения...
    return routes, metrics, unassigned
```
И передайте ее в `scripts/eval_algorithm.py`:
```bash
./venv/bin/python scripts/eval_algorithm.py --custom-solver my_file.py:my_custom_solver --preset vostok
```
Стенд автоматически:
1. Запустит базовый алгоритм FIFO (Baseline).
2. Запустит ваш кастомный алгоритм.
3. Замерит точное время выполнения (runtime в миллисекундах).

## 🗄️ 5. Где и как хранятся данные бэкенда? (SQLite & Multi-tenancy)

### 5.1. СУБД: Локальный SQLite
Все данные бэкенда хранятся в реляционной базе данных **SQLite** в файле:
```
./scheduler.db
```
(путь настраивается переменной окружения `DATABASE_URL=sqlite:///./scheduler.db`).

Подключение реализовано через **SQLAlchemy 2.0 ORM** ([`backend/Entities/base.py`](file:///work/time-scheduler/backend/Entities/base.py)) с флагом `connect_args={"check_same_thread": False}`, что обеспечивает высокую производительность и безопасность при асинхронных запросах FastAPI.

### 5.2. Сессионная изоляция (Multi-tenancy)
Каждый диспетчер идентифицируется уникальным ID (например, `disp_a8f3b9c1`). 
Все таблицы содержат колонку `dispatcher_id`:
* **`dispatchers`**: сессия диспетчера, активный датасет, время создания.
* **`engineers`**: бригады сектора данного диспетчера (координаты базы, навыки, смена, статус).
* **`tasks`**: клиентские заявки диспетчера (адрес, координаты, окна визита, приоритет, статус).
* **`schedule_records`**: текущие путевые листы инженеров (остановки, времена прибытия, пробег).
* **`plan_metrics_records`**: сохраненные агрегированные метрики плана (пробег, резерв, процент экономии).
* **`explanation_caches`**: сохраненные ИИ-обоснования решений по заявкам и инженерам.

### 5.3. Гарантированно уникальные идентификаторы диспетчера
В модели [`Dispatcher`](file:///work/time-scheduler/backend/Entities/dispatcher.py) реализован метод:
* `Dispatcher.create_unique(db, active_preset)`: генерирует неповторяющийся идентификатор вида `disp_{timestamp_ms}_{uuid8}` с обязательной верификацией по БД SQLite.
* Эндпоинт `POST /api/session/unique-id` создает изолированного диспетчера и загружает сырые данные выбранного сектора.
* **Принцип чистого листа (Clean Slate):** При создании новой сессии маршруты не рассчитываются заранее, а `metrics` равен `None`. Пользователь видит исходный список инженеров и заявок до тех пор, пока не нажмет кнопку «Распланировать» (`POST /api/schedule/optimize`).

## 🎯 7. Ключевые архитектурные решения

### 7.1. Двухуровневая структура поиска, тегов и транспорта (`tags.ts`)
В [`frontend/src/utils/tags.ts`](file:///work/time-scheduler/frontend/src/utils/tags.ts) реализована строгая 2-уровневая модель:
1. **Модификаторы поиска (Search Modifiers, одиночный выбор — radio pills):**
   * **Для инженеров:** `Все`, `На линии`, `Резерв`, `Сход` (строго без скобок), `Изменения`.
   * **Для заявок:** `Все`, `В графике`, `Не распределенные`, `Отмененные`, `Изменения`.
2. **Теги фильтрации (Tags, множественный выбор — multi-select pills):**
   * **Для инженеров:** 3 типа квалификации (`Локальные работы`, `Работы на подключение и дозаказы`, `Аварийные работы`) + **Теги транспорта** (`Автомобиль`, `Общественный транспорт`, `Велосипед`, `Пешеход`).
   * **Для заявок:** 3 типа квалификации + 2 уровня важности (`Срочная`, `Обычная`) + `Проблемная`.
3. **Интеллектуальная строка поиска:** фильтрует как по ФИО, транспорту, адресу и `#ID`, так и по тексту любого активного тега.
4. **Удаление отдельной вкладки «Проблемные»:** проблемные заявки теперь органично находятся прямо в едином списке заявок через тег «Проблемная» или фильтр «Не распределенные», исключая дублирование сущностей.

### 7.2. Интерактивная карта, кликабельные участки путей и фокус заявки
* **Кликабельные участки маршрутов (Requirement 4):** Каждый переезд между базой и остановками отрисовывается отдельным интерактивным сегментом с всплывающей подсказкой (километраж и время доезда). При клике на отрезок пути активируется единый фокус `createSegmentFocus`: на карте подсвечивается янтарный штриховой контур с плашкой `[🚗 N мин (M км)]` и кнопкой сброса `[✕]`.
* **Изоляция маршрута при выборе заявки (Requirement 5):** При клике на любую заявку в списке или на карте открывается карточка заявки, а на карте отображается **исключительно маршрут назначенного инженера** (все остальные маршруты скрываются). Если заявка не назначена — лишние маршруты не загромождают карту.
* **Leaflet SVG Engine:** Отрисовка через векторные SVG-линии на базе цветных тайлов CARTO Voyager.

### 7.3. Единый интерактивный вертикальный таймлайн (`VerticalTimeline.tsx`)
Во всем приложении (шторка инженера, список бригад, карточка заявки, панель под картой) используется **одна-единственная вертикальная структура расписания**:
* **Интервалы 1 час (08:00 – 22:00):** Расписание размечено часовыми засечками с метками (`08:00`, `09:00`, ..., `22:00`). Поверх часовой сетки хронологически накладываются события: старт смены, перегоны (с кнопкой быстрого перехода на карту), карточки визитов и окончание смены.
* **Две вариации:**
  * **Подробная (`detailed`):** в карточке инженера — полная информация по адресам, окнам клиента, тегам квалификации, кнопкам ИИ-обоснования и отмены.
  * **Краткая (`compact`):** в общем списке инженеров и карточке задачи — аккуратные плашки с номерами остановок, временем прибытия и доездом.

### 7.4. Единая модель взаимно-исключающей фокусировки (`MapFocusState`)
Интерфейс фокусировки исключает конфликты меню и гонки состояний:
```typescript
export interface MapFocusState {
  type: 'none' | 'task' | 'engineer_route' | 'travel_segment';
  taskId?: string | null;
  engineerId?: string | null;
  segment?: TravelSegmentFocus | null;
}
```
Выбор любого объекта (инженера, задачи или отрезка доезда) **гарантированно сбрасывает все остальные фокусировки**.

### 7.5. Оперативная карточка статуса плана (3 состояния внимания)
В панели KPI (`MetricsCard.tsx`) блок внимания динамически информирует диспетчера:
1. **«Нужно обновить» (Есть изменения):** если в сессию добавлены новые задачи или инженеры, которые еще не были распланированы.
2. **«Требует внимания» (N заявок вне графика):** если в текущем плане остались нераспределенные заявки из-за нехватки смен или навыков.
3. **«Штатный режим» (100% охват):** если все заявки успешно уложились в расписание и маршруты оптимальны.
